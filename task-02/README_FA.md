## پیاده‌سازی حافظه محلی برای گفتگوی پیوسته

مدل‌های زبانی ذاتاً بدون وضعیت (Stateless) هستند. برای حفظ بافت گفتگو (Context)، تاریخچه پیام‌ها باید نگهداری شده و با هر درخواست مجدداً به مدل ارسال شود.

### مقایسه دو رویکرد مدیریت حافظه:

| ویژگی | حافظه مدیریت‌شده سمت برنامه | حافظه مدیریت‌شده سمت ارائه‌دهنده |
| :--- | :--- | :--- |
| **هزینه توکن** | توکن ورودی یکسان است اما امکان هرس دقیق تاریخچه وجود دارد | ارائه‌دهنده حجم پیام‌ها را تعیین می‌کند |
| **هزینه ذخیره‌سازی** | رایگان (ذخیره در رم یا فایل محلی) | معمولاً به ازای هر Thread یا Vector Store هزینه دارد |
| **کنترل** | کنترل کامل روی System Prompt و کانتکست | دسترسی محدود درون جعبه سیاه ارائه‌دهنده |
| **انعطاف و عدم قفل** | سازگار با تمامی مدل‌ها و ارائه‌دهندگان | قفل شدن در API اختصاصی یک شرکت |
| **پیاده‌سازی** | نیازمند منطق کدنویسی مدیریت وضعیت | آماده از طریق شناسه‌های ترد |

رویکرد اول به دلیل کنترل کامل روی مصرف توکن‌ها و جلوگیری از وابستگی به ارائه‌دهنده انتخاب شد.

### استراتژی پنجره متحرک (Sliding Window):

جهت جلوگیری از انفجار سایز کانتکست و افزایش تصاعدی هزینه‌های API، از الگوریتم پنجره متحرک استفاده شد که تنها ۱۰ پیام آخر (۵ پیام کاربر + ۵ پاسخ مدل) را نگهداری می‌کند:

```python
WINDOW_SIZE = 10 # ۵ پرامپت اخیر کاربر + ۵ پاسخ مدل = ۱۰ پیام
```
